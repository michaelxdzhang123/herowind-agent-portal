文档定位

这是一份面向新手的 Continue 使用手册。它的目标不是一次性讲完所有高级能力，而是帮助你在 VS Code 中稳定完成下面几件事：

  1. 正确安装 Continue，并使用内部 config.yaml 配置本地大模型和补全模型。
  2. 会用 Chat 模式解释代码、分析报错、生成测试建议。
  3. 会给模型提供正确上下文，例如文件、终端报错、Git Diff、选中代码。
  4. 会用 Edit 模式安全修改小范围代码。
  5. 会用 Autocomplete 提高编码速度，但不盲目接受补全。
  6. 会用 Plan 模式让模型先读代码、先规划、暂时不修改。
  7. 会用 Agent 模式完成小范围真实任务，并学会看 diff、跑测试、回滚改动。
  8. 初步理解 Rules、Slash Prompts 和 MCP，为后续进阶智能体编程打基础。

你可以把 Continue 理解成 VS Code 里的 AI 编程助手。它不是只能聊天，也可以读取选中的代码、读取指定文件、解释报错、生成测试、修改代码、查看 diff，甚至在 Agent 模式下调用工具去读文件、搜索项目、创建文件、修改文件、运行终端命令。

01. 配置本地大模型和补全模型

1.1 安装 VS Code

Windows 用户请先下载并安装 VS Code：

https://code.visualstudio.com/

建议安装完成后确认 VS Code 可以正常打开项目目录。

1.2 安装 Continue 插件

在 VS Code 中打开扩展市场，搜索并安装：

Continue

安装后，VS Code 左侧活动栏会出现 Continue 图标。不同版本的图标样式可能略有差异，通常是一个机器人或 Continue 标识。

1.3 下载内部 config.yaml

安装 Continue 后，新手不需要自己手动选择大模型，也不需要自己编写模型配置。直接下载内部提供的 config.yaml，并复制到 Continue 配置目录即可。

内部配置文件下载地址：

http://172.28.21.141:3004/s/ADN/p/config-yaml-k6D8KdyR6n

Windows 默认目录：

C:\Users\<yourname>\.continue\config.yaml

macOS / Linux 默认目录：

~/.continue/config.yaml

注意：请把 <yourname> 替换成你的系统用户名。
如果 .continue 目录不存在，可以手动新建。

1.4 下载并放置 AGENTS.md

在 VS Code 中打开你的项目文件夹，并确认项目根目录中有且只有一个内部规范文件：

AGENTS.md

内部 AGENTS.md 下载地址：

http://172.28.21.141:3004/s/ADN/p/AGENTS-md-k6D8KdyR6n

推荐放置位置：

your-project/
├── AGENTS.md
├── package.json
├── src/
└── ...

AGENTS.md 的作用是告诉 Continue 和智能体：这个项目的背景、编码规范、测试命令、禁止事项、目录说明、提交要求等。新手不建议在同一个项目里放多个互相冲突的规则文件。

1.5 打开项目并启动 Continue

  1. 在 VS Code 中打开你的项目文件夹。
  2. 点击左侧或左下角的 Continue 图标。
  3. 选择 Start a new session。
  4. 确认当前模型是内部配置的 Qwen3 或团队要求的模型。
  5. 确认模式选择为 Chat。
  6. 点击 Start 开始会话。
  7. 在输入框里试着问：
请用中文说明你现在能帮我做哪些 VS Code 编程辅助工作。

如果模型可以正常回复，说明基础配置已经成功。

1.6 配置完成后的检查项

你应该确认下面几件事：

  • Continue 面板可以打开。
  • Chat 模式可以正常回复。
  • 左下角或模型选择器中能看到内部大模型。
  • Autocomplete 使用的是内部补全模型。
  • 项目根目录中存在 AGENTS.md。
  • config.yaml 已经放到正确目录。
  • 本地网络可以访问内部模型服务或网关服务。

1.7 本手册重点

后续内容重点讲：

  • Continue 在 VS Code 里面应该怎么用。
  • Chat 模式适合做什么。
  • 什么时候用 Edit，什么时候用 Agent。
  • 怎么给模型上下文。
  • 怎么写提示词。
  • 怎么避免 Agent 把项目改乱。
  • 新手应该按什么顺序练习。

02. Continue 的核心概念

2.1 Continue 不是一个单一功能，而是一组能力

Continue 里面常见的能力包括：

能力 作用 新手优先级
Chat 对话、解释代码、问问题、让模型给建议 最高
Edit 选中一段代码，让模型直接做小范围修改 高
Autocomplete 写代码时给行内补全建议 高
Plan 只读模式，让模型先看代码、搜索文件、制定方案，但不改文件 中高
Agent 工具模式，让模型读取文件、搜索代码、修改文件、运行命令 中高
Rules 项目规则，让模型长期遵守某些规范 中
Prompts 可复用提示词，把常用任务做成 / 命令 中
MCP 外部工具协议，把数据库、文档、GitHub、浏览器等能力接入 Continue 进阶

新手最容易混淆的是 Chat、Edit、Agent：

  • Chat 主要是“问”和“讨论”。
  • Edit 主要是“改选中的一小段”。
  • Agent 主要是“让模型自己找上下文并完成一个任务”。

2.2 Continue 效果好不好，主要取决于 4 件事

第一，模型能力

不同模型能力差异很大。Chat 正常不代表 Agent 一定稳定。
本地模型、补全模型、网关配置、上下文长度都会影响体验。

第二，上下文质量

模型只能基于它“看到”的内容回答。你给它的文件、选中的代码、终端报错、Git Diff、项目规则都会影响结果质量。

第三，任务边界是否清楚

不清楚的任务容易导致模型乱改。清楚的任务通常包含：

  • 要改什么。
  • 不要改什么。
  • 涉及哪些文件。
  • 输出什么结果。
  • 如何验证。
  • 有哪些限制。

第四，你是否审查结果

Continue 能提高效率，但不能替代代码审查。
尤其是 Agent 模式下，必须看 diff、跑测试、确认没有误改。

03. 第一次打开 Continue：你应该认识哪些界面

3.1 Continue 侧边栏

打开 Continue 后，你需要认识这些区域：

  1. 模型选择器：选择当前使用哪个模型。
  2. 模式选择器：在 Chat、Plan、Agent、Edit 等模式之间切换。
  3. 输入框：输入自然语言任务。
  4. 上下文区域：添加 @Files、@Terminal、@Git Diff 等上下文。
  5. 工具调用与权限提示：Agent 模式下经常出现，需要你确认。
  6. 代码 diff 区域：查看模型准备修改的内容，不要盲目接受。
  7. 会话历史：查看前面提出的问题和模型的回答。

3.2 常用快捷键

不同操作系统、VS Code 版本、Continue 版本可能略有差异。下面是常见快捷键：

快捷键 常见作用
Cmd/Ctrl + L 将选中代码发送到 Chat
Cmd/Ctrl + I 对选中代码进行 Edit
Cmd/Ctrl + . 切换模式或打开相关操作
Tab 接受 Autocomplete 建议
Esc 拒绝 Autocomplete 建议

如果快捷键冲突，请在 VS Code 中打开：

File / Preferences / Keyboard Shortcuts

然后搜索：

Continue

04. 各种模式的区别：Chat、Plan、Agent、Edit、Autocomplete

4.1 Chat 模式：问答、解释、讨论

Chat 模式最适合新手入门。

适合做：

  • 解释代码。
  • 分析报错。
  • 让模型给实现思路。
  • 让模型生成测试用例建议。
  • 做代码 Review。
  • 总结一个文件的职责。
  • 询问某个函数、类、接口、配置的作用。

不适合做：

  • 大规模自动修改。
  • 跨很多文件的重构。
  • 让模型直接执行命令。
  • 让模型在没有上下文时猜测项目结构。

4.2 Plan 模式：只读探索和规划

Plan 模式适合在你还不熟悉项目时使用。

适合做：

  • 陌生项目探索。
  • 改造方案制定。
  • 让模型先找相关文件。
  • 让模型列出风险和验证步骤。
  • 在改代码前让模型输出计划。

特点：

  • 通常只读，不直接修改文件。
  • 适合在 Agent 执行前作为准备阶段。
  • 新手做复杂任务前，建议先 Plan 再 Agent。

4.3 Agent 模式：工具模式

Agent 模式允许模型调用工具，例如：

  • 读取文件。
  • 搜索项目。
  • 创建文件。
  • 修改文件。
  • 运行终端命令。
  • 查看测试结果。
  • 根据失败结果继续修复。

适合做：

  • 修复一个小 Bug。
  • 新增一个小功能。
  • 为某个函数补测试。
  • 迁移一个小范围接口。
  • 对有限文件做重构。
  • 根据测试失败结果迭代修复。

不适合新手直接做：

  • “重构整个项目”。
  • “优化所有代码”。
  • “把整个系统换成新架构”。
  • “不用问我，自动改完所有问题”。
  • “删除无用文件并自动提交”。

4.4 Edit 模式：小范围定点修改

Edit 模式适合你已经知道要改哪段代码时使用。

适合做：

  • 补注释。
  • 改类型。
  • 加错误处理。
  • 把一段同步逻辑改成异步。
  • 优化一个函数的可读性。
  • 给一个函数补输入校验。

不适合做：

  • 跨文件修改。
  • 大范围搜索。
  • 需要理解整个项目的任务。

4.5 Autocomplete：边写边补全

Autocomplete 是行内补全能力。我们使用一个本地专门做代码补全的模型。

适合做：

  • 补全函数体。
  • 补全重复样板代码。
  • 根据上下文补全参数。
  • 补全测试断言。
  • 补全常见 if / try / catch / return 结构。

不适合做：

  • 替代设计思考。
  • 盲目接受所有建议。
  • 自动完成安全敏感逻辑。
  • 自动生成你看不懂的核心代码。

05. 新手推荐学习路线

建议按下面顺序学习，不要一上来就直接用 Agent 改大项目。

第一阶段：只用 Chat

目标：知道怎么问、怎么让模型解释代码。

练习：

请解释这个函数的作用。

请说明这段代码可能有哪些边界情况。

第二阶段：选中代码 + Chat

目标：学会把具体代码发给模型，而不是让模型凭空猜。

练习：

  1. 选中一段函数。
  2. 按 Cmd/Ctrl + L。
  3. 提问：
请按输入、输出、核心逻辑、潜在问题四部分解释这段代码。

第三阶段：学会添加上下文

目标：会用 @Files、@Terminal、@Git Diff。

练习：

@Terminal 请分析这段测试失败日志，告诉我最可能的原因和最小修复方案。

@Git Diff 请 review 我这次改动，重点看是否有逻辑问题、兼容性问题和测试遗漏。

第四阶段：学 Edit

目标：小范围安全修改。

练习：

  1. 选中一个函数。
  2. 按 Cmd/Ctrl + I。
  3. 输入：
请只修改这段代码，增加空值检查，不要改函数签名。

第五阶段：学 Autocomplete

目标：提高编码速度，但不盲目按 Tab。

练习：

  • 写函数名和注释，让补全模型生成函数体。
  • 接受前先读一遍。
  • 不合适就按 Esc 拒绝。

第六阶段：学 Plan

目标：在改代码前先探索。

练习：

请进入 Plan 模式，先阅读项目结构和相关文件，告诉我如果要给登录接口增加参数校验，需要改哪些文件。暂时不要修改任何文件。

第七阶段：学 Agent

目标：让模型完成一个小范围真实任务。

练习：

请在 Agent 模式下，为 src/utils/validate.ts 中的 validateEmail 函数补充单元测试。只允许新增或修改测试文件，不要修改生产代码。完成后运行对应测试，并给出 diff 摘要。

第八阶段：学 Rules 和 Prompts

目标：把团队规范长期沉淀下来，把常用任务做成可复用命令。

练习：

  • 写一条项目规则：所有回答默认中文。
  • 写一条项目规则：修改代码后必须说明验证命令。
  • 写一个 /review Prompt：用于提交前 Review。

06. Chat 模式入门：先把它当代码问答助手

6.1 打开一个适合练习的项目

新手不要一开始就拿几十万行的大项目练习。建议选择：

  • 一个小型前端项目。
  • 一个 Node.js 工具项目。
  • 一个 Python 脚本项目。
  • 一个你熟悉业务背景的项目。
  • 一个测试能跑起来的项目。

6.2 第一个问题

在 Continue Chat 模式中输入：

请用中文说明你现在能帮我做哪些 VS Code 编程辅助工作。

你应该能看到模型介绍它可以做代码解释、报错分析、测试生成、重构建议等。

6.3 让它解释当前文件

打开一个代码文件，选中一段函数，然后按 Cmd/Ctrl + L，输入：

请解释这段代码。请按照：
1. 总体作用
2. 输入输出
3. 核心逻辑
4. 依赖关系
5. 潜在问题
这五部分说明。

6.4 让它分析报错

运行项目测试或启动命令，如果出现报错，把完整报错加入上下文。

推荐提问：

@Terminal 请分析这个报错。请告诉我：
1. 最可能原因
2. 出错文件和行号
3. 最小修复方案
4. 修复后应该运行什么命令验证

6.5 报错信息要完整

不要只发一句“报错了”。应该包含：

  • 你运行的命令。
  • 完整错误堆栈。
  • 出错文件路径。
  • 最近修改过什么。
  • 期望结果是什么。
  • 实际结果是什么。

示例：

我运行 npm test 后失败。下面是完整终端输出。请不要直接改代码，先分析原因，并给出最小修复方案。

@Terminal

07. Chat 模式进阶：如何给模型正确的上下文

7.1 什么是上下文

上下文就是你让模型“看见”的材料，包括：

  • 自然语言说明。
  • 选中的代码。
  • 当前文件。
  • 指定文件。
  • 终端输出。
  • Git Diff。
  • 项目规则。
  • 报错堆栈。
  • 相关配置。
  • API 文档片段。

模型回答好不好，很多时候不是因为模型“聪不聪明”，而是因为你给的上下文是否准确。

7.2 最常用的上下文方式

上下文方式 适合场景
选中代码 + Cmd/Ctrl + L 解释局部代码、找局部 bug
@Files 指定某些文件让模型阅读
@Terminal 分析命令输出、测试失败、构建失败
@Git Diff 提交前 review、检查改动风险
当前文件 解释当前打开文件
AGENTS.md 提供项目规则和团队规范

7.3 给上下文的原则

原则一：只给相关文件

不要一次把整个项目都塞给模型。上下文越乱，回答越容易跑偏。

原则二：报错要完整

错误堆栈、命令、路径、版本信息都可能很重要。

原则三：让模型先确认理解

对于复杂任务，可以先问：

请先复述你对问题的理解，不要修改代码。如果你认为缺少上下文，请列出需要我补充的文件。

原则四：每次只推进一个目标

不要把“修 bug、重构、补测试、优化性能、写文档”全部放在一个任务里。新手最好一次只做一件事。

7.4 好问题和差问题对比

差问题：

这个项目有问题，帮我看看。

好问题：

我运行 npm test 时，user.service.test.ts 中的 should create user 测试失败。请结合 @Terminal 和 @Files 中的 user.service.ts 分析失败原因。先不要修改代码，只给出最小修复方案。

08. Chat 模式常用场景和提示词模板

8.1 解释代码

请解释这段代码。请按以下结构输出：
1. 总体作用
2. 输入参数
3. 返回值
4. 核心逻辑
5. 关键依赖
6. 边界情况
7. 潜在 bug
8. 新手需要注意的点

8.2 分析报错

@Terminal 请分析这个报错。请按以下结构输出：
1. 报错摘要
2. 最可能原因
3. 相关文件和行号
4. 最小修复方案
5. 可能影响范围
6. 修复后验证命令

8.3 代码 Review

@Git Diff 请 review 我这次改动。请重点检查：
1. 逻辑是否正确
2. 是否有兼容性问题
3. 是否有边界情况遗漏
4. 是否需要补测试
5. 是否有命名或可读性问题
6. 是否存在安全风险

请按“必须修改 / 建议修改 / 可以不改”分类输出。

8.4 生成测试用例

请为这个函数设计单元测试。请输出：
1. 正常输入场景
2. 边界输入场景
3. 异常输入场景
4. Mock 依赖说明
5. 推荐测试代码
6. 运行测试命令

8.5 理解陌生文件

@Files 请阅读这个文件，输出：

09. 代码块的 Apply / Insert / Copy 怎么用

Continue 回答中经常会给出代码块。不同操作适合不同场景。

9.1 Copy

作用：复制代码块。

适合：

  • 你只想手动粘贴。
  • 你还不确定是否要应用。
  • 你想先放到临时文件里比较。

建议：

  • 新手优先用 Copy。
  • 粘贴后自己检查格式和上下文。

9.2 Insert

作用：把代码插入到当前光标位置。

适合：

  • 插入一个新函数。
  • 插入一段注释。
  • 插入一段测试代码。
  • 插入配置片段。

风险：

  • 插错位置。
  • 缺少 import。
  • 与现有代码重复。

9.3 Apply

作用：让 Continue 尝试把代码块应用到文件中。

适合：

  • 模型已经明确知道要改哪个文件。
  • 改动比较小。
  • 你可以清楚看 diff。
  • 你知道如何回滚。

使用建议：

  1. Apply 前先读代码块。
  2. Apply 后必须看 diff。
  3. 不确定时不要直接接受。
  4. 接受后运行测试或构建命令。

9.4 新手推荐顺序

对于新手，建议优先级：

Copy > Insert > Apply

等你熟悉 diff 和回滚之后，再更多使用 Apply。

10. Edit 模式：小范围、定点修改代码

10.1 Edit 模式适合什么

Edit 模式适合“我已经知道要改哪一段”的情况。

适合任务：

  • 给函数补注释。
  • 增加参数校验。
  • 改进错误提示。
  • 优化一段 if/else。
  • 把重复逻辑提取成局部函数。
  • 给一段代码增加日志。

10.2 使用步骤

  1. 打开目标文件。
  2. 选中要修改的代码。
  3. 按 Cmd/Ctrl + I。
  4. 输入明确指令。
  5. 查看生成结果。
  6. 接受或拒绝。
  7. 保存文件。
  8. 运行测试。

10.3 好的 Edit 指令

10.5 Edit 模式检查清单

使用 Edit 后检查：

  • 函数签名是否被误改。
  • import 是否正确。
  • 业务逻辑是否保持一致。
  • 格式化是否符合项目规范。
  • 是否需要补测试。
  • 是否引入了不必要依赖。

11. Autocomplete：行内补全怎么用，怎么用得稳

11.1 Autocomplete 的作用

Autocomplete 会根据当前文件和附近代码，自动给出后续代码建议。它像一个“边写边补”的助手。

11.2 基本操作

操作 说明
Tab 接受建议
Esc 拒绝建议
继续输入 让模型重新根据你的输入补全
删除部分内容 重新触发上下文理解

11.3 适合接受的补全

可以考虑接受：

  • 明显重复的样板代码。
  • 简单 getter/setter。
  • 测试中的类似断言。
  • 和上文风格完全一致的分支。
  • 类型定义中规律明显的字段。

11.4 不建议直接接受的补全

需要谨慎：

  • 权限判断。
  • 金额计算。
  • 数据删除。
  • 安全校验。
  • 加密、签名、鉴权。
  • 数据库迁移。
  • 复杂异步逻辑。
  • 多线程/并发逻辑。

11.5 用得稳的技巧

  1. 先写清楚函数名和注释。
  2. 先写输入输出类型。
  3. 让上下文附近有类似代码。
  4. 每次只接受一小段。
  5. 接受后马上读一遍。
  6. 对核心逻辑写测试。
  7. 不要因为补全“看起来很完整”就直接信任。

你写：

 * Return true only for non-empty strings containing a single @ and a valid domain.
 */

Autocomplete 可能会补全函数体。接受前要检查：

  • 是否处理空字符串。
  • 是否处理多个 @。
  • 是否处理空格。
  • 是否处理大小写。
  • 是否符合项目要求。
  • 是否需要更严格的正则。

12. Plan 模式：让模型先读代码、先规划、暂时不修改

12.1 为什么需要 Plan 模式

新手常见错误是：还没搞清楚项目结构，就让 Agent 直接改。
Plan 模式的价值是让模型先探索、先理解、先列方案，降低误改风险。

12.2 Plan 模式适合场景

  • 陌生项目阅读。
  • 找功能入口。
  • 找接口调用链。
  • 找测试位置。
  • 评估改动影响范围。
  • 制定重构方案。
  • 在 Agent 执行前确认范围。

2. 当前流程说明

4. 风险点
5. 推荐执行步骤

12.4 让 Plan 输出可执行任务

请把上面的方案拆成 3 个小任务，每个任务都包含：
1. 修改目标
2. 影响文件
3. 验证命令
4. 回滚方式

12.5 Plan 结果如何使用

拿到 Plan 后，不要直接照单全收。你需要检查：

  • 是否遗漏关键文件。
  • 是否改动范围过大。
  • 是否违反项目规范。
  • 是否存在更小的实现路径。
  • 测试命令是否正确。
  • 是否需要先问团队同学确认。

13. Agent 模式：让 Continue 自动读文件、改文件、跑命令

13.1 Agent 模式是什么

Agent 模式下，Continue 不只是聊天。它可以根据任务调用工具，自动完成一系列步骤，例如：

  1. 搜索项目。
  2. 阅读相关文件。
  3. 制定修改方案。
  4. 修改文件。
  5. 运行测试。
  6. 根据测试失败继续修复。
  7. 输出结果总结。

13.2 Agent 适合的任务

适合：

  • 给一个函数补测试。
  • 修复一个明确的 bug。
  • 改一个小接口。
  • 给一个页面补一个小交互。
  • 修改一个配置项。
  • 根据 lint 报错做小范围修复。
  • 给一个模块生成 README 初稿。

13.3 Agent 不适合的任务

不适合新手直接做：

  • 大范围重构。
  • 跨业务线改动。
  • 修改权限系统。
  • 修改支付、金额、结算逻辑。
  • 删除大量文件。
  • 自动提交代码。
  • 自动发布。
  • 修改生产配置。
  • 修改安全策略。
  • 不看 diff 就接受所有改动。

13.4 Agent 模式的好提示词格式

推荐结构：

14. Agent 模式的安全工作流

14.1 新建 Git 分支

不要直接在主分支上让 Agent 工作。

git checkout -b continue-agent-demo

14.2 确认工作区干净

开始前运行：

git status

如果已经有你自己的未提交改动，要先提交、stash，或者明确告诉 Agent 不要碰哪些文件。

14.3 先 Plan，再 Agent

复杂任务推荐：

  1. Plan：让模型先读代码、列方案。
  2. 你审查方案。
  3. Agent：只执行方案中的第一个小任务。
  4. 看 diff。
  5. 跑测试。
  6. 再进入下一个任务。

14.4 不自动批准所有操作

Agent 可能会申请读取文件、修改文件、运行命令。新手不要自动批准所有操作。

你应该看清楚：

  • 它要读哪个文件。
  • 它要改哪个文件。
  • 它要运行什么命令。
  • 命令是否安全。
  • 是否会删除文件。
  • 是否会访问外部网络。
  • 是否会提交、推送或发布。

14.5 每次都看 diff

Agent 改完后必须查看：

git diff

重点看：

  • 是否改了不该改的文件。
  • 是否引入无关格式化。
  • 是否删除了重要逻辑。
  • 是否引入临时代码。
  • 是否把密钥、Token、内部地址写进代码。
  • 是否误改配置。

14.6 跑测试验证

根据项目类型运行对应命令：

npm test
npm run test
npm run lint
npm run build
pytest
go test ./...
mvn test

不要只相信 Agent 说“应该可以”。以实际命令结果为准。

14.7 回滚方式

如果 Agent 改乱了，可以使用：

git diff

查看改动。

git checkout -- path/to/file

回滚某个文件。

git reset --hard

回滚全部未提交改动。
注意：这个命令会丢弃所有未提交修改，执行前必须确认没有重要内容。

16. Rules：给 Continue 长期记住项目规范

16.1 Rules 是什么

Rules 是让 Continue 长期遵守的项目规范。对于内部项目，本手册优先使用项目根目录的 AGENTS.md 来沉淀规则。

常见规则包括：

  • 回答默认使用中文。
  • 修改代码前先说明计划。
  • 修改代码后必须说明验证命令。
  • 不允许引入新依赖，除非明确要求。
  • 不允许修改公共 API，除非明确要求。
  • 不允许读取或输出敏感文件。
  • 代码风格要和现有项目保持一致。
  • 测试失败不能假装成功。

16.2 AGENTS.md 示例

可以在项目根目录维护：

# AGENTS.md

## 项目说明

这是一个内部示例项目，主要用于演示 Continue 的 Chat、Plan、Edit 和 Agent 工作流。

## 通用规则

- 默认使用中文回答。
- 修改代码前先简要说明计划。
- 修改代码后说明改动文件和验证命令。
- 不要引入新依赖，除非用户明确要求。
- 不要修改公共 API，除非用户明确要求。
- 不要读取、打印或提交任何密钥、Token、证书、私钥文件。
- 遇到测试失败时，需要说明失败原因，不要直接声称完成。

## 常用命令

- 安装依赖：npm install
- 运行测试：npm test
- 运行 lint：npm run lint
- 构建：npm run build

## 代码规范

- TypeScript 项目优先保留现有类型风格。
- 函数命名使用 camelCase。
- 测试文件命名遵循 *.test.ts。

16.3 Rules 不应该写什么

不要把下面内容写入规则文件：

  • API Key。
  • 数据库密码。
  • GitHub Token。
  • 私有证书。
  • 生产环境地址和凭证。
  • 个人账号密码。
  • 不希望模型长期看到的敏感业务信息。

18. MCP 和外部工具：新手只需要先知道什么

18.1 MCP 是什么

MCP 可以理解为一种把外部工具接入 AI 编程助手的协议。通过 MCP，Continue 可能连接：

  • 数据库。
  • 文档系统。
  • GitHub / GitLab。
  • 浏览器。
  • 内部知识库。
  • 任务系统。
  • 日志平台。

18.2 新手阶段不需要深入配置 MCP

  1. Chat 能问清楚问题。

18.3 MCP 使用风险

  • 权限最小化。
  • 不暴露敏感数据。
  • 不允许模型随意写生产系统。
  • 对写操作和删除操作要人工确认。
  • 外部系统操作需要审计。

20. 常见问题排查

Q1：模型不回复怎么办？

检查：

  • config.yaml 是否放在正确目录。
  • API Key 或内部网关配置是否正确。
  • 当前网络是否能访问内部模型服务。
  • VS Code 是否需要重启。
  • Continue 插件是否启用。
  • 模型选择器是否选中了可用模型。

Q2：Continue 面板看不到模型怎么办？

检查：

  • config.yaml 文件名是否正确，不要写成 config.yaml.txt。
  • YAML 缩进是否正确。
  • 配置目录是否正确。
  • VS Code 是否打开了正确用户目录。
  • Continue 是否读取到了最新配置。
  • 是否需要 Reload Window。

VS Code 可执行：

Developer: Reload Window

Q3：回复质量差怎么办？

常见原因：

  • 上下文太少。
  • 上下文太乱。
  • 问题太宽泛。
  • 没有给具体文件。
  • 没有给完整报错。
  • 任务边界不清楚。
  • 让模型一次做太多事。

改进方式：

请先基于我提供的上下文说明你理解到的信息。如果缺少关键文件，请列出来。不要直接猜。

Q4：Agent 把代码改乱了怎么办？

先不要继续让 Agent 修。执行：

git diff

查看改动。

只回滚某个文件：

git checkout -- path/to/file

全部回滚未提交改动：

git reset --hard

注意：git reset --hard 会删除所有未提交改动。

Q5：快捷键冲突怎么办？

打开 VS Code Keyboard Shortcuts，搜索：

Continue

重新设置快捷键即可。

Q6：Autocomplete 不显示怎么办？

检查：

  • Continue 是否启用 Autocomplete。
  • 补全模型是否配置成功。
  • 当前文件类型是否被支持。
  • 光标附近是否有足够上下文。
  • 是否被其他补全插件覆盖。
  • VS Code 是否需要重启。
  • 网络或本地模型服务是否正常。

Q7：Agent 一直跑、一直改怎么办？

处理方式：

  1. 停止当前 Agent。
  2. 查看 diff。
  3. 回滚无关改动。
  4. 把任务拆小。
  5. 明确限制允许修改的文件。
  6. 先用 Plan 模式重新规划。

更好的提示词：

请只完成第一步：定位问题并输出原因。不要修改任何文件。

Q8：模型输出的代码我看不懂怎么办？

不要直接应用。可以继续问：

请逐行解释你刚才给出的代码，并说明为什么这样写。请指出我需要重点检查的地方。

Q9：模型建议引入新依赖怎么办？

先确认是否真的需要。可以问：

请给出不引入新依赖的方案，并比较两种方案的优缺点。

Q10：模型误用了项目不存在的命令怎么办？

让它读取项目脚本：

@Files package.json 请根据 scripts 字段告诉我应该运行哪些测试、lint 和构建命令。

21. 新手最佳实践清单

21.1 每次提问前

  • 明确目标。
  • 准备相关文件。
  • 准备完整报错。
  • 确认不让模型做超范围任务。
  • 对复杂任务先要求模型复述理解。

21.2 使用 Chat 时

  • 一次问一个问题。
  • 尽量给出文件和报错。
  • 要求结构化输出。
  • 不满意时让模型重新基于具体上下文回答。
  • 不要让模型凭空猜项目情况。

21.3 使用 Edit 时

  • 只选中需要修改的代码。
  • 明确“只修改选中代码”。
  • 明确“不要改函数签名”。
  • 明确“不要引入新依赖”。
  • 修改后运行测试。

21.4 使用 Autocomplete 时

  • 小段接受。
  • 接受前先读。
  • 关键逻辑不要盲目 Tab。
  • 核心业务逻辑要补测试。
  • 对安全、权限、金额相关代码特别谨慎。

21.5 使用 Plan 时

  • 让模型先读文件。
  • 明确“暂时不要修改”。
  • 要求输出文件列表、风险点和验证命令。
  • 审查方案后再执行。

21.6 使用 Agent 时

  • 新建分支。
  • 确认工作区干净。
  • 限制修改范围。
  • 禁止自动提交。
  • 不自动批准所有操作。
  • 每次看 diff。
  • 每次跑测试。
  • 失败就停下来分析，不要无限循环。
  • 必要时回滚。

21.7 安全红线

不要让模型读取、输出、修改、提交以下内容：

  • API Key。
  • 密码。
  • 私钥。
  • 证书。
  • 生产数据库连接串。
  • GitHub Token。
  • 内部敏感文档。
  • 用户隐私数据。
  • 生产环境配置。
  • 发布脚本中的敏感参数。

  8. 能用 Plan 输出一个修改方案。

附录 B：推荐的第一次真实练习任务

选择一个你熟悉的小项目，完成下面流程：

git checkout -b continue-first-practice
git status

然后在 Continue Chat 中提问：

请阅读这个项目的 AGENTS.md 和 package.json，告诉我：
1. 这个项目可能是什么类型
2. 常用测试、构建、lint 命令是什么
3. 新手应该先读哪些文件
4. 使用 Agent 时需要注意哪些限制

暂时不要修改任何文件。

接着选择一个小函数，使用 Edit 模式：

请只修改选中的代码，增加必要的空值检查。不要修改函数签名，不要引入新依赖。

最后查看 diff：

git diff

运行测试：

npm test

如果结果正常，说明你已经完成了一次完整的 Continue 入门实践。
